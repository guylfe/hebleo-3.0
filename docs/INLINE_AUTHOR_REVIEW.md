# Inline authoring and private review (FIRST2-F14)

31 October 2026. Bounded implementation for the Lead's fourteen-item candidate. Local demo only; no installed database, main branch, WordPress, source curriculum or media files were changed. Owner verification is separate from independent review and Guy acceptance.

## Workflow and canonical owners

An existing `canAuthor` profile sees **Edit lesson** and an author-comment count in the lesson. Editing uses the same lesson container, source page IDs, reading measure and sanitized rich renderer. The existing local Markdown/HTML adapter edits the original source string; it never serializes rendered `innerText` or strips unknown source metadata. Headings, source text, explicit component Extra information, existing page settings (prompt, choices, answer, feedback/model, timing, media, gate) and existing activity settings can be edited. Activity/item IDs and activity kinds stay fixed. No new teaching, answers or media are supplied by this feature. Advanced settings use labelled JSON fields, matching the existing text-page editor's supported source settings.

`public/studio/workspace.js` is the shared full-workspace/base/token/CAS coordinator extracted from unified Studio. Both interfaces use it. All mounted Studio collectors contribute before a save; inline changes do not start a separate draft or overwrite sibling vocabulary/exercise/curriculum edits. Existing imports/source reviews retain their own deliberate staging paths and reset the in-memory coordinator only after successful staging. Server validation and source freshness/approval remain authoritative.

Save draft retains the server's returned token. Inline **Preview saved draft** requires a clean saved workspace and opens the existing disposable learner rehearsal. It writes no learner answers, completion or settings. **Apply changes** opens Studio's existing Changes & history/impact surface; its **Publish saved draft** remains the separate release action. Source-bound releases still require the existing Sources & import approval/freshness path; inline Apply cannot bypass that server gate. The historical Studio rehearsal of a saved draft continues to exclude unsaved form values explicitly; inline Preview is stricter and requires saving them first.

Read/edit toggles, page/component switches and the move from inline authoring into Studio retain local work. Leaving Studio for another app destination keeps the existing Save draft / Discard / Stay guard. Unsaved private comments are protected separately: saving teaching text does not silently send or discard a review note. Actual browser unload warns when work remains. Raw invalid settings, unsent bodies and request IDs remain in memory across local view changes; they are deliberately not put into localStorage. Reload requires saving first. A 400/403/409/network failure keeps the inputs. A 403 revokes further submission. Compare latest is read-only; **Reconcile nonconflicting changes** is an explicit three-way merge. Overlapping authored changes refuse reconciliation and retain local values; there is no automatic retry using somebody else's token. An author may compare, copy the needed text, and explicitly reload/discard before resolving a genuine overlap.

Private review is also available under Studio's Comments & replies task, separately from the unchanged learner discussion/moderation area. It uses the same source context and review controls. No private comment is inserted into lesson HTML, public questions, source/library search, learner bootstrap/session, or content JSON exports.

Canonical UI map: source editor = `studio/markdown-editor.js`; learner/rehearsal renderer = `rich.js` + `text-reader.js`; server draft/publication = Store's existing stage/impact/publish/source gates; native selects/dialogs and notifications = current app primitives; shared typography/colors/reading measure/scrollbars = `refinement.css` tokens. `author/author.css` only supplies flow, wrapping and author-specific spacing. English controls and exact authored Hebrew/Nikkud remain unchanged.

## Author API

The local demonstration's existing `x-demo-user: author-demo` scope is required on **every** author read/write. Both fictional learners receive 403. This reuses the current capability boundary; it is not production authentication or a new assistant credential. An authorized local assistant can read these same author endpoints. Do not expose the demo server publicly.

* `GET /api/studio/author-comments?lessonId=...&status=all|open|resolved&limit=50&cursor=0`: full private records, `total`, `nextCursor`. Limit is 1–100. Insertion-order offset pagination; status filtering can change totals. Optional `revisionId` reads the requested historical context. The UI includes filter, previous/next, count, original source context/audit and stable-context jump controls.
* `GET /api/studio/author-comments/projection?lessonId=...&componentId=...&pageId=...&activityId=...&fieldPath=html&baseRevisionId=...&draftToken=...`: exact server projection, hash and UTF-16 offset convention. Empty optional identifiers and token mean null. Every identifier must resolve in the named saved revision or exact current saved draft. Unsaved text cannot be anchored.
* `POST /api/studio/author-comments`: `{requestId,lessonId,baseRevisionId,draftToken,componentId,pageId,activityId,fieldPath,selection,body}`. Use a UUID request ID; optional hierarchy IDs, `draftToken`, and whole-field `selection` are explicit null. Body is plain text, 1–8000 code units with nonblank content; it is escaped when displayed. Server derives ID, actor, author-only visibility, times, anchor hash/snapshot and initial audit. Same actor/request/exact original body returns the same record, even after restore; changed content with the same request ID returns 409.
* `POST /api/studio/author-comments/:id/status`: `{requestId,expectedVersion,status:"open"|"resolved"}`. Resolve/reopen appends an actor/time/version audit row. A retry returns the current record for the same operation. A stale expectedVersion or conflicting request ID returns 409 without mutation. There is no deletion endpoint.

The comment-create JSON keys are strictly allowlisted. No client-supplied actor, visibility, hash, timestamps, arbitrary JSON paths or HTML interpretation is accepted. Example requests belong to synthetic tests, never fabricated Guy comments.

## Anchors and projections

An immutable anchor contains lesson/component/page/activity IDs, saved revision ID, optional saved draft token, allowlisted field, projectionVersion 1, full source-text snapshot, SHA-256 and optional exact quote/context/range. The HTML/Markdown projection is `textContent` from the **same** sanitized renderer used by the learner. It does not fold spaces or normalize Unicode. Offsets count JavaScript UTF-16 code units; surrogate splits, forged quotes, context mismatches and altered Nikkud reject atomically. Quote prefix/suffix are server-derived up to 80 units each. A labelled read-only source field supports keyboard selection as well as selection over rendered source. If the selected text cannot be verified against the saved field, the UI explicitly uses a whole-field comment.

Allowlisted text fields are page `html/title/prompt/explanation/answer/extraInformation`, component `text/extraInformation/options.extraInformation`, and lesson `title/explanation/extraInformation`; string activity `prompt/instruction/title` are supported through explicit paths. Non-string fields reject. Whole `activity` comments require the exact existing activity ID and use canonical sorted-key JSON of that activity plus its page prompt/options/answer/explanation/timing/value/media/gate. This pins settings/answer/feedback changes, including retained unknown activity metadata, without inventing option or paragraph IDs.

Listing compares the original anchor with the current saved workspace (or requested historical revision):

| State | Meaning |
|---|---|
| current | Same field hash, or a single exact quote match within the same stable field. Relocation returns `currentSelection` and `relocated:true`; original anchor remains immutable. |
| changed | Field changed and the original quote cannot be uniquely located, or a whole-field snapshot changed. No approximate Hebrew matching. |
| missing | The stable lesson/component/page/activity no longer resolves. No substitution by title, index or next paragraph. |
| historical | Explicit historical revision, or a retained page retired from active order. Original context stays readable. |

Private comments do not create publication gates. Draft-context snapshots are retained in the private review namespace so a note can still be read and validated after the draft is replaced or published. Current anchors never silently mutate the original selection/snapshot.

## Storage, recovery and integration

Store/backup reader **10**; review namespace `author-review` has schemaVersion **2**. Reader 9 / namespace 1 remains a supported legacy input. Older executables reject reader 10 databases/backups. Without an existing review namespace, reader-8 migration changes only the schema marker. Legacy full contexts are validated and compacted in the same transaction as the new marker; comments, immutable create receipts, status audits, original quotes/hashes, tokens, revisions and learner rows retain their values.

Each retained draft has its exact immutable `baseRevisionId`, SHA-256 `baseHash` of canonical full base content, and a lossless JSON-tree delta. Delta tags are `v` (replacement), `o` (object removals/field changes), `a` (array length/index changes), and `r` (SHA-256 reference to a namespace `chunks` entry); null means unchanged. Object changes are sorted deterministically, arrays retain every position/value, and unknown fields are included. Large immutable delta nodes (at least 4096 UTF-8 bytes) are carried once by content hash. This matters on the real workspace: about 18 MB of lexical data exists only in the saved draft, so repeatedly carrying that addition against the published base would still grow each context. No history is removed and no mutable draft is used as a reconstruction base. Full reconstruction verifies base hash, chunk hashes/structure and the original complete draft token before validating the original field/UTF-16 quote. Reconstructed contexts participate in media recovery, identity and lexical trust checks.

Backups and the app's downloaded backup file use the same compact JSON serialization. Source strings, including HTML/Markdown whitespace, remain exact. The shared 200,000,000 UTF-8 byte bound applies to export eligibility, app file selection and the restore HTTP body. An oversized export returns HTTP 413 `BACKUP_TOO_LARGE` before any artifact is sent; it retains all stored data. Compact formatting avoids whitespace alone tripling the full workspace backup. This does not promise unlimited authoring history: legitimately distinct large edits/media may eventually require a different recovery format; export refuses honestly at the current bound. Oversized historical reader-9 files still exceed the HTTP bound; the supplied six-context legacy database is recovered by lossless database migration, followed by an eligible export.

Restore validates the entire incoming namespace and every referenced saved source, token, hash, quote, actor, audit/version chain and duplicate before writes. Matching revision snapshots are paired one-to-one in ascending incoming/existing ID order within each content hash. Only unmatched incoming identities append rows; distinct identical-content revisions remain distinct. Repeating the same backup or export/restore reuses the same mapping without revision/context growth. Navigable pins relink only when required; immutable client create receipts remain original for idempotent recovery. An older/legacy restore retains newer local private notes and prefix-compatible audit history. Diverging history/request collisions reject instead of dropping feedback. Rollback changes content revisions, never private review. A restore failure inside the transaction rolls back the namespace, content, media, learners and SQLite ID sequence together. Older backups missing media needed by a retained private draft context refuse restoration rather than silently losing it.

The installed reader-8 database must be copied/backed up, migrated through the normal Store constructor on a disposable candidate, and compared before a reader-10 preservation release is installed. `scripts/update-first2-feedback.mjs` now accepts marker-only reader-8 migration and lossless reader-9 review compaction, with exact semantic comparison of all private review data. It uses a consistent read-only SQLite `VACUUM INTO` copy after the asynchronous backup worker stalled in this Windows environment. No live migration was run.
