# Autoplay checkbox persistence

Guy requested fixing the WordPress autoplay checkbox and checking the native equivalent. This patch does not add settings or change defaults, Nikkud, curriculum, card ordering, audio content or review scheduling.

The installed save handler previously used `isset($_POST['autoplay_audio']) ? 1 : 0`. The frontend always sends either 0 or 1, so both choices saved as enabled. Separately, the settings template treated database string `"0"` as truthy and checked the box. `generate.mjs` guards the exact live two-file baseline, changes only that value handling and that rendering expression, and emits a hash manifest. Explicit integer/string 0/1 and booleans are supported; legacy checked `on` is supported and an omitted checkbox remains off. Invalid values return an error before replacing settings. The saved checkbox uses `Number(value) === 1`. Existing front/back playback already respects numeric 0/1, including the managed shared-card player, and needs no change.

The previous new-card ordering fix remains present. Loader baseline is the installed `5d7ae367` version, not an older plugin snapshot. The generated loader SHA256 is `32a4f89f2f85f78e978780191b798633b8a71c7864788ec0f6582e73756cccd7`; archive SHA256 is `216bb8b90828dcf834ad03bbca8fa55a189d5f07c20d48adc856aa245ce159cf`. Unchanged order helper SHA256 is `cae48431a38c03563b156c473753539acb7c82c2b491042f1c20b20f3ca0f536`.

`install.php` uses the existing release lock, exact before/after hashes, private backups of both originals outside the web root, atomic replacements, targeted opcode invalidation, protected-state comparison, and guarded rollback of both code files. No broad cache purge, preference rewrite, content migration or review action runs. `protected.php` fingerprints 14 groups, including every progress/settings/session row, authored post metadata, schedules/burial, other plugin files including the ordering helper, and shared-card media. Live immediate before/after fingerprints matched exactly.
